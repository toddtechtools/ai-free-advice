The filesystem is the runbook.

When the number in a filename is the execution order, a colleague or a fresh AI session can recover the declared sequence by sorting the files. The README records prerequisites and recovery steps, the runner validates the sequence, and the final verify step checks the result.

00

Why order is the contract

A multi-step procedure has two parts: the steps, and the order of the steps. Most teams write down the first and keep the second in someone’s head. That works right up until the person — or the AI session — that holds the order is gone.

Putting the run order into the filename moves it out of anyone’s head and into a visible, mechanically checkable place: the directory listing. The prefix stops being decoration and becomes a contract.

If the prefix is only cosmetic

Humans and other AIs still have to guess the sequence. A number that “roughly” suggests order is worse than no number, because it looks trustworthy.

When the number is the execution order

Sorting the files reproduces the workflow exactly. The work survives AI downtime, model changes, staff changes, and your own memory.

Who this protects:

  • You, later. Three months from now you won’t remember whether fix-podman.sh runs before or after configure.sh.
  • A colleague on call. At 2 a.m. they need to re-run the deploy, not reverse-engineer it.
  • Another AI model. A new session has no conversation history. It can read the README, inspect the declared sequence, and use the same runner a teammate would use.
01

The core rule

Naming + runtime order (mandatory)
  1. Every sequenced script, playbook step, or ordered artifact uses a zero-padded prefix: 00-…, 01-…, 02-…, 03-…
  2. For scripts, the number is the execution order. 00 runs first, then 01, then 02. For goals, projects, and documents, it defines presentation, portfolio, or reading order; dependencies are recorded separately. Never create a script that must run before a lower number or after a higher number without renaming.
  3. A human or another AI must be able to read the sequence from the filenames, find prerequisites and recovery steps in the README, and execute the pipeline through the runner.
  4. Before writing any files, output a short ordered plan (number + one-line purpose). Then create exactly those names.
# Inspect the declared pipeline order from inside the collection:
printf '%s\n' [0-8][0-9]-*.sh | LC_ALL=C sort

Use this listing to inspect the order. Use the runner to validate and execute the pipeline. The README is a document index, so it may share 00 with the first executable step; two executable steps may never share a number.

      03

      How problems expand without order

      Missing order doesn’t fail once and stay put. Each new unnumbered file adds ambiguity on top of the existing ambiguity, and the cost lands on whoever touches it next.

      1. Day 1
        Five scripts, one author, everything works

        The author runs them in the right order from memory. No problem is visible yet, which is why the habit takes hold.

      2. Week 2
        fix-podman.sh is added

        It must run between install and configure. Only the author knows that. The order now lives in one head.

        orderings to guess: 6! = 720
      3. Month 2
        install2.sh and helper.sh appear

        Is install2 a replacement or an addition? Is helper run or sourced? Nobody can tell from the names, and the AI session that wrote them has ended.

        orderings to guess: 8! = 40,320 — plus “which ones run at all?”
      4. Hand-off
        A colleague or new AI sorts and runs

        Configure runs before install. It fails partway, leaving a half-configured host. They retry, re-running non-idempotent steps. The host now differs from every other host.

        cost: a broken host plus configuration drift
      5. Incident
        Nobody can reproduce or roll back

        Rollback has to undo steps in reverse order — an order no one recorded. The fix becomes archaeology: reading shell history, old chats, and timestamps. The cost is no longer a failed run; it’s lost trust in the whole procedure.

        cost: time, trust, and a postmortem
      40,320
      possible orders when names carry no sequence
      1
      possible order when the number is the run order

      Without numbers, n steps have n! possible permutations (n × (n−1) × … × 1). This is a mathematical upper bound on arrangements, not a measured failure rate: dependencies may allow several valid orders, and documentation can resolve ambiguity. Numbering selects one declared sequence; it does not prove the sequence or the scripts are correct.

      04

      The zero-padding trap

      Numbers without padding sort as text, not as numbers. Once you pass nine steps, the order silently breaks.

      Unpadded ls | sort

      • 1-check-prereqs.sh1st
      • 10-verify.sh2nd?!Verify runs before anything is installed.
      • 11-rollback.sh3rd?!Rollback runs third, in the middle of a deploy.
      • 2-create-dirs.sh4th
      • 3-install-packages.sh5th
      • …

      Zero-padded ls | sort

      • 01-check-prereqs.sh1st
      • 02-create-dirs.sh2nd
      • 03-install-packages.sh3rd
      • …
      • 10-verify.sh10th
      • 99-rollback.shmanual

      Split before planned growth would exceed prefix 80. Zero-based 00–80 provides 81 positions. Steps 81–89 are executable by the runner, but they are not planned capacity — a collection that reaches them has already outgrown itself and should have split. Keep 90–99 manual-only for executable collections. Never add 100 to a two-digit collection: it sorts before 11. See section 09 for capacity and split rules.

      05

      The solution: four patterns that survive AI downtime

      One directory is one linear pipeline

      A directory holds exactly one sequence. If you have deploy and backup procedures, they live in separate directories, each starting at 00.

      deploy/
  00-README.md            # run order + purpose of each step (read first)
  00-check-prereqs.sh     # podman, cgroup v2, SELinux
  01-create-dirs.sh
  02-install-packages.sh
  03-configure-podman.sh
  04-write-quadlets.sh
  05-start-services.sh
  06-verify.sh            # exits non-zero on failure: hand-off gate
  99-rollback.sh          # manual only; never run by the runner
  run-all.sh              # the one unnumbered entry point

      An explicit runner, so nobody has to remember

      Any multi-step script set ships with a runner that executes the steps in sorted order and stops on the first failure. Before executing a step, the runner checks for the README and validates top-level shell-script filenames, regular executable files, unique prefixes, a contiguous pipeline from 00, and a final verify filename. A gap or duplicate from a partial renumber blocks execution. Review the README and verification logic to confirm the intended sequence and outcome. See section 06 for why it’s named run-all.sh rather than 00-run-all.sh.

      #!/usr/bin/env bash
# run-all.sh — validate first; run only 00–89, never manual 90–99.
set -euo pipefail
export LC_ALL=C
cd -- "$(dirname -- "${BASH_SOURCE[0]}")"
unset GLOBIGNORE GLOBSORT
set +f
shopt -u failglob nocaseglob nocasematch
shopt -s nullglob dotglob
fail() { printf 'run-all: %s\n' "$*" >&2; exit 1; }
[[ -f 00-README.md ]] || fail 'missing 00-README.md'
# Reject stray scripts, invalid names, symlinks, and duplicate prefixes.
declare -A seen=()
for f in *.sh; do
  [[ $f == run-all.sh ]] && continue
  [[ $f =~ ^([0-9]{2})-[a-z0-9]+(-[a-z0-9]+)*\.sh$ ]] || fail "invalid step: $f"
  prefix=${BASH_REMATCH[1]}
  [[ ! -L $f && -f $f && -x $f ]] || fail "not a regular executable: $f"
  [[ ! ${seen[$prefix]+present} ]] || fail "duplicate prefix: $prefix"
  seen[$prefix]=1
done
steps=( [0-8][0-9]-*.sh )
(( ${#steps[@]} > 0 )) || fail 'no pipeline steps found'
for i in "${!steps[@]}"; do
  f=${steps[$i]}
  prefix=${f%%-*}
  (( 10#$prefix == i )) || fail "gap: expected position $i, found $f"
done
last=${steps[${#steps[@]}-1]}
[[ $last =~ ^[0-8][0-9]-verify\.sh$ ]] || fail 'last step must be NN-verify.sh'
for f in "${steps[@]}"; do
  printf 'Running %s\n' "$f"
  "./$f"
done
printf 'All %s pipeline steps passed.\n' "${#steps[@]}"

      Dependencies only flow forward

      03 may depend on results from 01 and 02 after the runner completes them successfully. It must not call earlier steps to repeat them implicitly. A standalone invocation must check its prerequisites; ordering is not evidence that a previous run happened. 01 must never require 03. If a later step turns out to be needed earlier, renumber the whole set (section 07). Never leave an out-of-order name in place with a comment saying “run this first.”

      Document the order in a 00 file

      The filenames carry the order; 00-README.md carries the why. It is the explicit read-first index. Under C sorting, uppercase README sorts before lowercase step names sharing 00.

      00-README.md

Run order (execute ./run-all.sh):
  00-check-prereqs.sh    – verifies podman, cgroup v2, SELinux enforcing
  01-create-dirs.sh      – creates ~/.config/containers/systemd and data dirs
  02-install-packages.sh – dnf installs pinned packages
  03-configure-podman.sh – rootless storage + registries
  04-write-quadlets.sh   – writes .container/.network units
  05-start-services.sh   – reload systemd and start the generated units
  06-verify.sh           – must pass before hand-off

Manual only:
  99-rollback.sh         – stops units, removes quadlets (reverse of 05→04)
      06

      Runner traps to avoid

      The obvious runner — loop over [0-9][0-9]-*.sh — has several failure modes that show up the first time someone uses it for real.

      TrapWhat happensFix
      Runner named 00-run-all.shIt matches its own glob and calls itself, forever. It also shares 00 with 00-check-prereqs.sh, so two files claim “first.”Name it run-all.sh: the one allowed unnumbered entry point, outside the pattern.
      99-rollback.sh in the same globEvery successful deploy ends by rolling itself back.Reserve 90–99 for manual operations; the runner globs [0-8][0-9]-*.sh.
      Sort depends on localeSome locales ignore punctuation or fold case when sorting, so two hosts can order the same files differently.export LC_ALL=C in the runner for byte-order sorting everywhere.
      Spaces or odd characters in namesfor f in $(ls …) splits 02-install packages.sh into two words.Lowercase, hyphens, no spaces. Iterate a glob array, not $(ls).
      Octal arithmetic on 08/09Bash reads a leading zero as octal: $((08+1)) is an error.Force base 10: $((10#$n + 1)).
      07

      Inserting a step

      You need a firewall step between 02-install-packages.sh and 03-configure-podman.sh. The tempting shortcuts all break the contract.

      Wrong patch it in

      • 02-install-packages.sh
      • 02a-firewall.sh✗A numbered glob alone skips it. The guide’s runner rejects it during validation.
      • 02.5-firewall.sh✗Same problem, and the decimal invites 02.25 next month.
      • 03-firewall.sh✗Collides with 03-configure-podman.sh; filename suffixes determine which 03 runs first, rather than an explicit step position.
      • firewall.sh # run after 02!✗The order is back in a comment — tribal knowledge again.

      Right renumber everything after it

      • 02-install-packages.shsame
      • 03-configure-firewall.shnew
      • 04-configure-podman.shwas 03
      • 05-write-quadlets.shwas 04
      • 06-start-services.shwas 05
      • 07-verify.shwas 06

      Renumber from the highest file downward so nothing gets overwritten. Use git mv to stage each rename and update 00-README.md in the same commit. Revalidate the complete collection before running it. The runner detects visible gaps and duplicates, and a reviewed change keeps the scripts and references in sync.

      Renumber as a reviewed change
      1. Inspect the entire collection and plan every source → destination rename before changing anything.
      2. If planned growth crosses 80, split first (section 09) — do not cross into 90–99.
      3. Use git mv, highest number first, then create the new step with a two-digit prefix.
      4. Update 00-README.md, links, tests, configuration, and every filename reference in the same change.
      5. Keep permanent IDs unchanged and revalidate the complete sequence.

      When adding work to an existing pipeline, insert it before the final verify step and move verification forward. “Continue from the highest number” applies within the same collection and range; a manual 99 does not determine the next pipeline number.

      08

      One convention across all work

      Use two-digit, lowercase, hyphen-separated names within each collection. Each folder owns its numbering; there is no single global sequence. Existing collections continue their sequence; a genuinely new child collection starts its own sequence.

      ObjectExampleMeaning
      Goal01-repeatable-delivery.mdPresentation or priority order
      Project02-agent-execution/Portfolio order
      Phase03-agents-and-skills/Planned delivery order; dependencies explicit
      Document04-design-overview.htmlReading order
      Pipeline step04-validate-runtime.shMandatory runtime order
      Manual script99-rollback.shManual only; never automatic

      Replace mixed display labels such as P0 and G1 with a clearly named collection and zero-padded display positions. A goal numbered 02 does not automatically depend on goal 01.

      Every collection has 00-README.md. Document and folder entries normally start at 01 because 00 is the index. Executable steps start at 00: script and document numbering are separate scopes. Keep tool-required filenames such as AGENTS.md and SKILL.md intact and list them in the index; keep source modules and third-party assets in their appropriate directories rather than numbering code symbols or vendor files.

      09

      Split at 80: the math and operation

      Split before a collection’s planned sequence would exceed 80. This threshold concerns the highest planned prefix, not “80 files.” Split into meaningful stages instead of arbitrary buckets of 80.

      RangeCapacityUse
      00–8081 positionsNormal pipeline planning, including final verification
      01–8080 entriesDocuments or folders, plus their 00 index
      81–899 positionsExecutable, but never planned — reaching them means the split is overdue
      90–9910 positionsManual operations in script collections; excluded from runners

      The executable address space is 00–89 (90 steps). The planning limit is deliberately lower; 81–89 are a warning signal, not spare room to budget against. Two-digit non-executable collections also split at 80; do not treat 90–99 as a second tranche of planned documentation.

      02-pipeline/
  00-README.md
  run-all.sh
  00-prepare.sh       # invokes 01-prepare/run-all.sh
  01-deploy.sh        # invokes 02-deploy/run-all.sh
  02-verify.sh        # verifies the integrated result
  99-rollback.sh      # manual; documents scope and reversal order
  01-prepare/
    00-README.md
    run-all.sh
    00-preflight.sh
    01-prepare-workspace.sh
    02-verify.sh
  02-deploy/
    00-README.md
    run-all.sh
    00-configure.sh
    01-start-services.sh
    02-verify.sh

      Parent numbered steps invoke child runners synchronously and propagate any non-zero exit. Each child finishes and verifies before a dependent stage starts. Each directory has exactly one runner for its own executable collection. Never recursively glob the whole tree, run children twice, or require a later sibling to prepare an earlier one. The parent README records the complete stage order and links each child README.

      Insertion cost: with n steps numbered from 0, insertion before position p renames n − p existing files. Inserting before 05 in 00–19 moves 15 files. If all n + 1 insertion positions are equally likely, the average is n/2 renames. Keep collections small and permanent references independent of these positions.

      10

      Stable identity, changeable order

      A filename prefix describes where an item sits today. A permanent ID identifies the same item throughout its life. Store IDs in document metadata or an index; scope them to the program and never reuse retired IDs.

      filename: 01-repeatable-delivery.md
id: GOAL-000017
order: 01
title: Repeatable delivery

# After reordering:
filename: 04-repeatable-delivery.md
id: GOAL-000017
order: 04

      Use permanent IDs in acceptance criteria, dependency records, and audit evidence. Use paths for navigation; update those links whenever paths change. If order metadata is present, validate it against the filename rather than maintaining two conflicting orders. This is a naming convention, not a requirement to add a database or new service.

      12

      Paste-in instruction block

      Drop this into a skill, AGENTS.md, or any system prompt. It’s written so a model with no prior context can follow it.

      ## Ordered work, naming & runtime sequence (NON-NEGOTIABLE)

- Apply scoped two-digit ordering to goals, projects, phases, documents,
  and executable procedures. Use lowercase hyphen-separated names; no spaces.
- Each folder owns its collection and has 00-README.md. Document/folder
  entries start at 01; executable steps start at 00 (separate scopes).
- Preserve tool-required filenames such as AGENTS.md and SKILL.md;
  list these exceptions in the index. Shared shell code lives in lib/.
- Within each ordered collection: unique, contiguous numeric positions;
  no 02a, decimals, mixed widths, duplicate executable prefixes, or hidden gaps.
- Split before planned growth would exceed prefix 80. 00–80 means
  81 positions; 01–80 means 80 entries. Do not treat 81–89 as spare
  capacity. Never extend to 100.
- 00–89 are executable pipeline positions; 90–99 are manual-only
  operations and are never executed by the runner.
- For scripts, LC_ALL=C filename order MUST equal runtime order.
  For goals/projects/documents, order is presentation/reading order;
  dependencies must be recorded separately.
- Each executable collection has exactly one unnumbered run-all.sh:
  set -euo pipefail; export LC_ALL=C; validate the entire direct-child
  script set before any step runs; reject invalid names, duplicate
  prefixes, gaps, symlinks, non-executable steps, empty pipelines,
  and a missing final NN-verify.sh; execute sorted [0-8][0-9]-*.sh;
  stop on first failure; never execute itself or manual 9x scripts.
- A step may depend only on lower-numbered steps. It does not silently
  re-run them; standalone execution checks prerequisite state.
- Existing collections continue their sequence, not a new 00. Insert
  added work before the existing final verify step. Manual 99 does
  not determine the next pipeline number.
- Before insertion, plan all renames. Use git mv highest first, then
  update the README, links, tests, configs, and filename references.
  A gapped collection must never execute; the fail-closed runner
  refuses to run mid-renumber.
- Split by meaningful stages: numbered parent steps invoke child
  runners synchronously and propagate failures. Each child has its own
  README and final verification; the parent ends with integration
  verification. No recursive global glob or duplicated child execution.
- Keep permanent IDs unchanged during moves or renumbering; never reuse
  retired IDs. Use IDs for traceability and paths for navigation.
- The README lists ordered entries, purposes, dependencies, manual
  operations, exceptions, and child procedures. A stranger must recover
  the complete procedure without any prior conversation.
- When creating multiple steps: first list exact filenames and one-line
  purposes in order; then create exactly those names.
- No final.sh, do_it.sh, helper.sh, or utils.sh as pipeline steps.
- Verification must fail non-zero on any failed required check. Missing
  evidence is NOT EXECUTED/HOLD, never PASS. A numbered name, mock run,
  or successful syntax check alone does not prove host readiness.
